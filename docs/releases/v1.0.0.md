# v1.0.0 — Bilingual Semantic Search with Qwen3-Embedding-4B + Qdrant
> 🌐 Language / Ngôn ngữ: **English** | [Tiếng Việt](v1.0.0.vi.md)

## Summary

`v1.0.0` is the first public release of `nodejs-qdrant-bilingual-search`: an English/Vietnamese open-geography semantic-search API built with Node.js, Hono, Qdrant and Qwen3-Embedding-4B.

The accepted portable profile runs the embedding model with **Transformers / PyTorch / CPU / FP16** while exposing normalized **Float32[2560]** vectors over `binary-f32` transport. The canonical Qdrant snapshot contains 20,000 verified entities.

## Release history and provenance

The repository history was reconstructed for reviewability after the original `v1.0.0` publication. The original tag referenced the prior history. After the reconstructed `main` lineage was independently revalidated, `v1.0.0` was retargeted to the final documentation-closeout commit in that lineage.

Historical clean Kaggle production-demo evidence from 2026-08-31 remains valid for reconstructed source commit `b316619ad94947571e91124adfe96071bbd1f255` and tree `ff28454332cf976d1fb8fb17262924b09ca92cd2`. It is retained as historical qualification evidence and is not relabeled as evidence for a later rewritten release tip.

The final `v1.0.0` publication policy binds the canonical notebook to the annotated `v1.0.0` tag rather than a moving `main` branch. The notebook fails closed unless its checkout resolves to that annotated tag's commit. The final controlled runtime-evidence asset is defined as the evidence ZIP produced by a fresh Kaggle **Restart Session → Run All** from the exact frozen tag target. Its timestamp and SHA-256 are recorded in the GitHub Release and machine-readable release manifest after independent review rather than being hard-coded here before the run exists.

GitHub-generated **Source code (zip)** and **Source code (tar.gz)** archives are produced directly from the annotated `v1.0.0` tag and are outside the controlled custom-artifact checksum manifest.

- `Qwen/Qwen3-Embedding-4B`, 2560 dimensions, cosine distance.

- Public embedding vectors are normalized `Float32[2560]`.
- Reproducible Node.js CI on Node 22 and Node 24.

- Separate `runtime/true-fp32` engineering/reference branch.

## Stable compatibility sentinels

```text
Thailand EN = PASS
Tokyo VI    = PASS
Beijing VI  = PASS
```

A separate stricter relation-style diagnostic set remains intentionally scoped as diagnostic-only:

- Thailand VI capital-form can produce a Bangkok-city vs Thailand-country near-tie, so the expected country is not necessarily rank #1 after the strict entity-type consistency gate.
- Fuji/Japan EN/VI remains a known relation-style diagnostic miss.

The same city-over-country ordering was reproduced on the proven true-FP32 reference profile with slightly different scores. That supports the conclusion that this ordering is not specific to FP16; it does not imply byte-identical outputs across dtypes.

## Reproduction

Canonical Kaggle CPU-FP16 startup:

```bash
export QDRANT_STORAGE_PATH=/kaggle/working/qdrant-bilingual-search/qdrant-data
bash scripts/kaggle/run-qwen3-transformers-fp16-cpu.sh
```

The wrapper resolves the model read-only from `/kaggle/input`, enforces the accepted CPU-FP16 contract, enables offline loading and launches the production-demo lifecycle.

Verification commands:

```bash
npm run verify:canonical-config
npm run verify:semantic-index -- 20000
npm run seed:status -- --once --expected 20000
npm test
```

## Known limitations

- Portable CPU demo/runtime, not low-latency GPU serving.
- No reranker.
- No hybrid sparse+dense retrieval.
- No RAG layer.
- No automatic runtime reseeding.
- Relation-style diagnostics can expose ranking limitations even when canonical semantic verification passes.

## Reference work

`runtime/true-fp32` retains the proven prebuilt true-FP32 CPU implementation as an engineering/reference branch. The canonical `v1.0.0` profile remains CPU FP16 because it provides more practical memory headroom on Kaggle.
